## Purpose in ATAR
ATAR's primary user interface is a full-screen terminal application per Section 7. Textual provides the App framework, screen management, widget composition, CSS styling, keyboard handling, and testing infrastructure.

## Official Terminology
- **App:** The main application class — subclass `App`, call `app.run()`
- **Screen:** A full-terminal content area — switch with `app.push_screen()`, `app.switch_screen()`
- **Widget:** Composable UI component — `Header`, `Footer`, `Input`, `Static`, `RichLog`, `ListView`, `Tree`, `DataTable`, etc.
- **Compose:** Method returning child widgets via `compose()`
- **CSS/TCSS:** Textual's CSS dialect for styling — selectors, properties, classes
- **Worker:** Background async task via `@work` decorator
- **Command Palette:** Built-in fuzzy command search via `CommandPalette`
- **Pilot:** Automated test harness for TUI testing
- **Reactive:** Auto-updating attributes that trigger UI refresh
- **Application Mode:** Full-screen terminal takeover via alternate screen buffer

## App Lifecycle
1. `__init__()` — constructor
2. `compose()` — return child widgets
3. `on_mount()` — called after entering application mode
4. `on_key()` — keyboard events
5. Event handlers (`on_*`) — respond to widget events
6. `action_*` — named actions for key bindings
7. `app.exit()` — clean shutdown

## Keyboard Model (Section 7.4)
```text
Ctrl+K        Command palette → Binds to action "command_palette"
Ctrl+P        Quick file open → Screen push with search
Ctrl+Enter    Submit input → Action on Input widget
Ctrl+C        Interrupt → app.exit()
Esc           Close/back → Screen pop
```
Bindings are configured via `BINDINGS` class variable.

## Screens
ATAR requires 23 screens per Section 7.3. Implementation: one Python class per screen, inheriting `Screen`. Navigation via `push_screen()` / `pop_screen()` / `switch_screen()`.

## Testing
Textual provides `pilot` for async UI testing:
```python
async def test_app():
    async with MyApp().run_test() as pilot:
        await pilot.press("ctrl+k")
        assert pilot.app.screen.id == "command_palette"
```

## Known Incompatibilities
- Textual 8.x dropped Python 3.8/3.9 support
- Inline mode not supported on Windows
- Some Unicode characters may not render correctly in all terminals
- `aiohttp` conflicts possible (use `httpx` instead for ATAR)

## Security Requirements
- TUI must NEVER execute tools directly — typed commands to application services only
- Secret fields in provider setup must use `Password` widget (masked)
- Clipboard access requires user consent on some platforms

## Required Contract Tests

3. Keyboard shortcut mapping
4. Widget mounting and reactivity
5. Streaming text output (RichLog)
6. Resize behavior

## Open Questions
- None — Textual is well-documented and mature

## Implementation Decision
Use Textual 8.2.8 for full-screen TUI. Build screens incrementally per milestone order. Do NOT let TUI import provider SDKs, SQLAlchemy, or tool implementations directly — communicate through application services and events.

## Evidence
- Textual docs confirmed: v8.2.8, Python 3.8+ (3.12 for ATAR)
- App lifecycle: compose → on_mount → event handlers → exit
- Screens: push_screen, pop_screen, switch_screen
- Workers: @work decorator for background tasks
- Testing: pilot with run_test() async context manager
- CSS: TCSS with full property support, dark/light themes
